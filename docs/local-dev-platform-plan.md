# Service Manager 转型需求计划

状态：实施基线。本文描述目标与发布门槛，实际通过项见 [验证记录](development-verification.md)。

更新：2026-11-07。按用户补充，仅支持 Apple Silicon（arm64），浏览器验收只使用 Chrome；首版软件范围为 PHP、Node.js、MySQL、PostgreSQL、Redis、MongoDB；配置通过图形界面完成，并纳入 UI E2E。

同日来源调整：按用户最新要求，PHP 改为 `shivammathur/php` Homebrew tap，PostgreSQL 改为 Homebrew core 版本公式。本文后续历史里程碑中“不要求 Homebrew”的条件对这两类软件不再适用。其他软件仍使用 App 校验下载；项目尚未发布，清理旧测试安装和数据，不做旧来源兼容或数据迁移。

## 1. 产品方向与首版目标

将现有 macOS Service Manager 转型为开源的本地开发环境管理工具。以本地域名、可信 HTTPS 和反向代理为核心，提供运行时版本管理、开发服务管理和数据库管理。

**首版闭环：在 macOS 上“导入项目 → 配置环境 → 启动服务 → 用本地域名访问”。**

第一版同时交付上述四类能力。下文的里程碑是同一个首版内部的实施顺序，不代表把运行时或数据库移出首版。

产品原则：

- 项目是主要入口。用户关心“这个项目能否访问、缺什么、哪里出错”，不必先理解 launchd。
- 本地 HTTPS 可以独立使用。已有 `localhost:3000` 服务也能直接获得 `https://app.test`。
- PHP、PostgreSQL 使用 Homebrew 管理二进制与依赖；其他软件下载经过校验的发行包，在应用管理的目录中安装和运行。
- App 管理二进制包及实例配置；服务进程统一复用现有 `internal/launchd` 和 `launchctl` 能力，由 macOS launchd 托管生命周期。
- 版本按项目选择。二进制可共享，配置、端口、日志和数据库数据按实例隔离。
- 支持任意语言启动的 HTTP 服务。首版直接管理 PHP 和 Node.js，项目模型不绑定单一语言。
- 核心功能开源、无需账户、无站点数量限制。安装完成后，本地运行不依赖云端。

首版面向在 macOS 上开发 Web 应用的个人开发者和小团队。直接提供 PHP、Node.js 运行时，以及 MySQL、PostgreSQL、Redis、MongoDB 实例管理。已有 Go 与 Valkey 后端保留兼容。

## 3. 当前项目基础

本计划基于当前受 Git 跟踪的 Go + MyGo 实现。工作区存在未跟踪的 `ServiceManager/` Swift 目录，本次不修改，也不将其视为迁移目标。

| 已有基础 | 代码位置 | 转型处理 |
| --- | --- | --- |
| 原生窗口、菜单栏、列表与详情 | `main.go`、`menubar.go`、`view*.go` | 保留技术栈，增加项目入口及新的详情页面 |
| 服务模型及 Provider 接口 | `internal/service/service.go` | 保留系统服务接口；新增项目、包、实例、站点模型 |
| Homebrew 服务发现与启停 | `internal/brew/brew.go` | 保留为已有服务兼容入口，不作为新环境安装基础 |
| launchd 任务管理、环境变量及日志路径 | `internal/launchd/` | 复用底层能力，新增应用自有任务命名空间和归属记录 |
| 命令执行、超时和管理员授权 | `internal/system/system.go` | 增加下载任务、取消、流式输出及受限系统配置操作 |
| 文件日志尾部读取 | `internal/logs/logs.go` | 复用，增加轮转、筛选和敏感信息处理 |
| 单元测试、签名与公证发布脚本 | `*_test.go`、`.github/workflows/`、`scripts/package.sh` | 扩展真实环境集成测试和二进制发行验证 |

当前主要缺口：项目配置与持久化、软件包下载和版本解析、独立服务实例、数据库初始化与备份、反向代理、证书信任、域名映射、跨模块任务编排。

现有 `service.Provider` 面向“已经存在的启动项”，不能直接承担软件安装、项目依赖和数据库数据生命周期。新增领域模型，通过适配层调用现有服务能力。

核查方式为阅读代码和配置；本次未执行构建、测试、签名或公证，不把已有脚本等同于发布链路已验证。

旧版系统服务管理继续可用。首版不增加这部分的业务范围，也不自动接管用户已有的 Homebrew 服务或数据库目录。

## 5. 核心用户流程

### 5.1 导入项目

1. 用户选择本地项目目录。
2. 应用读取已有项目配置；没有配置时，识别 `package.json`、`.nvmrc`、`.node-version`、`go.mod` 等，提出建议。
3. 展示项目名、运行时、启动命令、工作目录、环境变量、依赖服务、端口和域名。
4. 用户可以修改并确认；导入本身不执行项目脚本，不安装项目依赖。

识别结果只是建议。多个版本声明冲突时展示来源，由用户选择；已有本产品配置优先，不能静默改写仓库里的其他工具配置。

### 5.2 配置环境

1. 用户选择运行时版本和数据库/缓存实例。
2. 应用展示缺失软件、下载来源、预计体积和要创建的数据目录。
3. 下载、校验并安装缺失版本；创建独立数据库实例和连接凭据。
4. 展示项目依赖安装命令，用户主动执行，例如 `npm ci`。这类命令可能运行仓库脚本，操作记录必须与运行时安装区分。
5. 保存项目声明、解析后的版本锁和本机配置。

若只代理已运行的本地服务，用户可跳过运行时和数据库配置。

### 5.3 启动服务

1. 检查二进制、端口、工作目录、环境变量及依赖关系。
2. 按依赖顺序启动数据库、缓存和应用进程。
3. 等待健康检查成功，再将站点标记为可访问。
4. 失败时显示具体失败步骤及相关日志，允许修正后重试。

进程存在不等于服务就绪。数据库、应用、代理和证书应分别报告状态。

### 5.4 用本地域名访问

1. 用户设置 `app.test`，上游为项目内部的 `127.0.0.1:<端口>`。
2. 首次启用可信 HTTPS 时，应用说明本地 CA 的用途，并通过 macOS 授权完成必要的信任和域名配置。
3. 应用签发证书并加载代理规则，用户点击“打开网站”。
4. 后续重启项目保留域名。内部端口变化时，代理更新到新的目标。

预期结果：浏览器访问 `https://app.test` 无证书警告，应用的热更新、WebSocket 和流式响应正常。

## 6. 功能需求与验收标准

### FR-01 项目与配置（P0）

- 项目拥有稳定 ID，可关联多个服务、数据库实例和站点；移动目录后可以重新定位。
- 声明文件建议命名为 `devmanager.json`，包含 `schemaVersion`；版本锁为 `devmanager.lock.json`。命名是暂定方案。
- 可共享声明只保存相对目录、运行时要求、启动参数、依赖和站点建议；绝对路径、实际端口、凭据及 CA 状态留在本机。
- 本机项目注册使用稳定 ID 关联共享声明；同一仓库的不同工作副本可创建独立实例。
- 不覆盖现有 `.env`。支持引用已有文件；生成的本地秘密文件需限制权限并提示加入忽略规则。
- 配置写入采用原子替换、格式校验和版本迁移；不支持的 schema 明确报错。

验收：两个不同目录的项目可独立配置和并行启动；重启应用后配置恢复；移除项目只移除管理关系，不删除源代码和数据库数据。

### FR-02 本地域名、HTTPS 与反向代理（P0）

- 创建、编辑、停用、删除站点规则；至少支持一个项目多个明确域名和不同上游。
- 默认域名为 `<project>.test`；首版采用受管理的 hosts 条目，不自建通用 DNS 服务，不支持通配 hosts。
- 仅修改应用自己的 hosts 区块；更新前校验冲突和备份，保留其他内容，处理外部并发修改。
- 默认监听回环地址，不自动开放局域网或公网。IPv4/IPv6 映射必须与实际监听一致。
- 默认入口为 HTTPS 443；检测 80/443 被占用时展示占用信息和可选端口，不停止其他程序。非标准端口须明确显示在 URL 中。
- 为本产品生成独立 CA；用户显式授权后安装信任。不得静默信任未知 CA，也不复用其他软件的 CA 私钥。
- 自动为配置的域名签发与续期证书；展示有效期、信任状态、修复入口和移除信任入口。
- 代理支持 HTTP/HTTPS 上游、WebSocket、SSE、大文件上传，以及可配置连接/响应超时；HTTPS 上游默认验证证书。
- 支持 Host/转发头策略，保留请求路径和查询参数；配置预览中提示上游的 allowed hosts、HMR origin 等可能需要调整。
- 上游不可用时返回清晰的本地错误页面，区分解析、证书、代理和应用错误。
- 配置先校验再热加载；失败时保留上一份有效配置，不中断其他站点。

验收：两个项目使用不同域名和内部端口，同时通过可信 HTTPS 访问；WebSocket/HMR、SSE 和上传测试通过；模拟上游退出及错误代理配置时，其他站点继续可用。

首版承诺本机访问。手机或另一台电脑需要独立解决域名解析和 CA 信任，不宣称自动获得可信 HTTPS。Chrome 为首版验收浏览器；其他浏览器不作为本次验收要求，命令行客户端提供独立信任诊断，不建议通过关闭 TLS 验证解决。

### FR-03 二进制下载与版本管理（P0）

- 软件目录展示名称、版本、架构、最低系统版本、来源、体积、校验信息和支持状态。
- 下载到缓存目录，校验后解压到临时目录，验证可执行文件，再原子安装到版本目录。
- 支持进度、取消、失败重试及缓存复用；中断安装不能留下“已安装”的假状态。
- 对归档路径穿越、越界符号链接及可疑安装脚本进行限制；不执行来源任意的远程 shell 脚本。
- 按精确版本和架构保存包；版本目录不可被原地升级。使用中的版本不能卸载。
- App 维护包清单、安装目录和实例引用关系；launchctl 只管理使用这些包启动的服务，不承担包下载、安装或升级。
- 项目锁记录精确版本、包来源及摘要。缺失锁定版本时明确失败，不能静默替换成最新版。
- 项目进程及 CLI 使用选定版本的绝对路径和环境；不要求修改系统 Node/Go，不默认修改 shell 启动文件。
- 支持手动关联已有可执行文件，但必须标记“外部管理”，不承诺可下载复现或负责升级卸载。

验收：两个项目并行运行不同 Node.js 版本；一个 Go 项目使用指定版本执行；系统默认版本不变；损坏包、架构不符和下载取消均有明确结果。

### FR-04 开发服务与编排（P0）

- 服务包含程序和参数、工作目录、环境变量引用、依赖、健康检查、重启策略及日志。
- 每个托管实例生成独立 launchd job，使用稳定标签、选定版本的绝对路径及独立配置。启动、停止、重启、自启动和进程状态查询复用现有 launchctl 适配能力。
- 参数默认按数组传递；仅在用户明确配置 shell 模式时解释 shell 字符。
- 启动顺序按依赖关系计算，拒绝依赖环；健康检查支持进程、TCP 和 HTTP，设置超时。
- 明确区分停止、启动中、运行但未就绪、健康、失败和停止中。
- 支持启停重启、优雅退出和停止超时处理；自动重启策略限定为 launchd 能可靠表达并经过验证的策略，默认关闭自动重启。配置重启节流并诊断频繁崩溃；首版不承诺自定义指数退避或严格重启次数上限。停止时验证所属子进程已退出。
- 项目停止按反向依赖顺序执行；共享服务仍被其他运行项目引用时保留。
- 启动失败只回收本次新建或新启的资源，不停止原本已运行的共享服务，不删除数据。
- 默认不随登录启动项目。用户可以逐项目开启；关闭窗口继续运行，退出应用时明确选择保留或停止自有服务。
- 外部进程允许作为代理目标和只读连接对象；未接管的进程不能被“一键停止项目”误杀。

验收：数据库就绪后应用才启动；端口冲突可修正后重试；默认策略下崩溃不自动重启，启用自动重启时节流生效且可手动停止；两个项目共享一个实例时停止其中一个不影响另一个。

### FR-05 数据库与缓存管理（P0）

- PostgreSQL 支持下载选定版本、创建独立实例、初始化、启停、健康检查和日志。
- 实例具有独立数据目录、配置、端口和版本绑定；默认回环监听并生成访问凭据。
- 支持创建数据库和用户、授予指定数据库权限、复制连接信息，以及打开外部客户端。
- 支持使用匹配版本工具完成逻辑备份与恢复；展示任务进度和错误。恢复默认写入新数据库，覆盖已有数据需明确确认。
- 卸载二进制、移除实例记录和删除数据分别处理。被引用的包不能卸载；删除数据必须显示实际路径与影响。
- 首版不支持跨 PostgreSQL 大版本切换数据目录，不将“选择新版本”伪装成数据迁移。
- Redis 支持独立实例、认证、连接信息、持久化设置和编号数据库备份恢复；清空数据是单独的破坏性操作。
- 共享实例必须明确显示使用它的项目；凭据通过本机密钥存储或受限文件提供，不进入可共享配置或普通日志。

验收：创建两个 PostgreSQL 实例及同名数据库，端口和数据互不影响；完成“写入测试数据 → 逻辑备份 → 恢复到新数据库 → 校验数据”；删除项目后数据仍存在；Redis 重启后的行为符合选定持久化策略。MySQL、MongoDB 同样验证认证、建库、用户及备份恢复。

数据库管理在首版指实例生命周期、数据库/用户创建、连接和备份恢复，不包含完整 SQL 编辑器、表格编辑器或可视化数据库建模。

### FR-06 诊断（P0）

- 不提供对外 CLI。所有操作在 GUI 中完成；可执行文件的 `--dev` 入口只服务 App 自己的 launchd 任务、worker 和终端 Node 版本选择。测试与验证脚本使用 `cmd/devmgr`，它不随 App 发布，也不作为接口维护。
- 并发操作排队或返回资源占用原因，GUI 与后台任务使用同一项目与版本锁。
- `doctor` 检查软件包、运行时、端口、域名映射、CA 信任和上游健康，给出具体修复步骤。
- 导出诊断报告前移除密码、令牌和私钥；访问日志默认不记录请求体和敏感请求头。

验收：GUI 配置的项目可在 GUI 中启停；项目命令使用项目选定版本；故障报告能定位问题发生在哪一层。

| --- | --- |
| 项目列表 | 名称、域名、运行状态、失败原因、一键启动/停止 |
| 项目详情 | 总览、环境、服务、站点、日志；突出“打开网站” |
| 导入向导 | 目录识别 → 配置环境 → 安装与初始化 → 启动并访问 |
| 站点 | 域名、上游、证书状态、代理状态；允许不绑定项目 |
| 运行时 | 可用版本、已安装版本、被哪些项目使用、安装任务 |
| 数据库 | 实例、版本、端口、连接、数据库/用户、备份恢复 |
| 系统服务 | 保留已有 Homebrew、launchd 和登录项管理 |
| 设置 | CA 信任、存储目录、网络入口、开机行为、诊断与清理 |

菜单栏优先展示项目状态和常用站点，保留进入原服务管理界面的入口。首次启动围绕导入项目和 HTTPS 设置，不再把完整磁盘访问权限作为新用户主流程；旧登录项功能需要时再展示原有引导。

## 8. 技术方案与边界

### 8.1 延续现有技术栈

继续使用 Go + MyGo。新增共享的应用控制层，将耗时任务和业务状态从 `app.go` 中逐步分离。UI 只发起操作并订阅结果。

建议模块边界：

| 模块 | 职责 |
| --- | --- |
| `internal/project` | 项目声明、版本锁、导入与迁移 |
| `internal/packages` | 软件目录、下载、校验、安装与引用关系 |
| `internal/runtime` | 项目运行时选择与命令环境 |
| `internal/instance` | 实例配置、包引用、依赖编排、健康检查，通过 launchd 适配层管理进程 |
| `internal/proxy` | 站点模型、配置生成、热加载，代理进程同样交给 launchd 托管 |
| `internal/certificates` | CA 生命周期、信任状态、证书状态 |
| `internal/database` | MySQL/PostgreSQL/Redis/MongoDB 实例适配与数据库任务 |
| `internal/platform` | hosts、信任、系统授权等 macOS 专用能力 |
| `internal/control` | GUI/CLI 共用操作、资源锁和任务事件 |

复用现有 `launchd`、`logs`、`system` 模块。`internal/launchd` 是所有托管服务的统一进程管理入口；包管理层提供绝对路径，实例层生成任务配置，UI 和 CLI 通过共享控制层调用。新模块名为建议，不要求一次性重构所有旧代码。

### 8.2 代理与证书

实施决定：使用 Go 标准库 crypto/x509、TLS 和 httputil.ReverseProxy 提供本地 CA、域名证书和代理。没有引入 Caddy 二进制。默认 443 由 launchd socket activation 监听，代理进程降为当前用户；协议和真实浏览器验证见验证记录。

本产品拥有独立配置和数据目录；本地域名明确使用内部签发策略，不尝试为 `.test` 申请公网证书。CA 信任由应用管理，避免代理后台自行触发不可解释的授权。

`.test` 用于测试域名，依据 [RFC 2606](https://www.rfc-editor.org/info/rfc2606/)。首版通过 hosts 映射具体域名；不把 `.local` 当作任意通用后缀，不承诺手机自动发现。

代理和开发进程默认以普通用户身份运行。hosts、系统信任及必要的网络配置走受限系统操作：只允许明确的配置变更，不允许把任意项目命令以 root 执行。80/443 的绑定方式必须在最低支持 macOS 上验证；如需额外权限，使用最小化的系统适配方案，不能让整个项目栈以 root 运行。

### 8.3 软件包来源

PHP 使用用户指定的 `shivammathur/php` tap，PostgreSQL 使用 Homebrew core 的 `postgresql@<major>`。其他软件优先级为：上游可验证的二进制发行包 → 已审核的第三方发行包 → 本项目可复现构建的发行包。安装失败时不在这两种管理方式之间静默回退。

实施来源：Node.js/MySQL/MongoDB 使用上游归档，PHP 使用 shivammathur/php，PostgreSQL 使用 Homebrew core，Redis 使用官方 Redis Stack 包中的原生 redis-server。Homebrew 选择的系列解析为含 revision 的精确 Cellar 版本，安装收据须匹配 tap。数据、端口、配置与 launchd 实例仍由 App 独立管理，不启动 Homebrew 默认服务。许可证仍由各软件包自身决定。

后续若增加没有合适发行包的软件，应在受控构建环境产出包，不能把编译器和完整依赖链留给最终用户安装。

软件目录必须记录来源、许可证信息、精确版本、平台、摘要及健康检查方法。项目维护的目录和构建包需有签名验证；仅从下载地址同时取得哈希，不能替代可信来源校验。首版不开放任意第三方安装脚本插件。

### 8.4 存储与数据归属

暂沿用现有应用标识，避免首版同时引入系统权限身份迁移。应用管理目录示意：

```text
<AppSupport>/
  catalog/                         # 已验证的软件目录元数据
  packages/<name>/<version>/<arch>/ # 按版本保存的二进制及依赖
  instances/<id>/                  # 配置、实例元数据及数据库数据
  projects/<id>/                   # 本机覆盖配置、关联与任务状态
  proxy/                          # 代理配置及 CA 私有数据
  backups/                        # 用户发起的备份
<Caches>/downloads/                # 可清理的下载缓存
<Logs>/                           # 可轮转的运行日志
```

配置、缓存、包和数据库数据分别管理。数据库数据不是缓存；清理缓存、升级应用和卸载运行时都不能连带删除数据。私钥和凭据只对所属用户开放，不进入同步清单或诊断包。

原生进程隔离只表示版本、配置、端口和数据路径隔离，不表示容器或安全沙箱。

### 8.5 App 管包，launchd 管进程

职责分工固定为：

| 执行方 | 负责内容 |
| --- | --- |
| App / 共用业务层 | 下载校验、版本目录、实例配置、数据库初始化、依赖就绪检查、站点配置与证书信任 |
| 现有 launchctl 适配层 | 生成与校验 plist、注册与移除 job、启停重启、查询状态、配置自启动 |
| macOS launchd | 托管已注册服务进程，执行配置的生命周期和重启策略 |

代理、项目开发服务器与各数据库按实例注册为用户级任务；低端口入口使用 launchd socket activation，代理仍以当前用户运行。标签使用应用专属前缀和存储目录摘要；同一二进制版本可供多个 job 使用，各有独立参数、环境、工作目录和日志。

运行时本身是软件包，不是常驻服务。例如 Node.js 版本由 App 管理，使用该版本启动的项目服务器才是 launchd job。下载、校验和初始化属于有限时准备任务；数据库备份/恢复/建库/建用户，以及项目依赖安装和 CLI `exec`，由 App 自管的有限时 launchd worker 执行。调用方退出后持久记录继续保护资源，GUI 提供显式审阅与收尾，不自动重放写入命令。

首版不另建常驻进程监管器，也不要求单独的常驻控制进程或 IPC 服务。GUI 和 CLI 复用同一 Go 业务层，通过跨进程文件锁和原子状态写入协调操作。GUI 退出后，已托管的服务可继续由 launchd 运行。

依赖编排与健康检查仍由 App/CLI 完成，不能把 job 已加载当作服务就绪。用户开启项目登录自启时，通过 launchd 调用同一程序的项目启动入口，按依赖顺序等待就绪后退出；不依赖多个独立 job 的登录启动顺序。

版本切换流程为：准备并验证新包 → 停止受影响实例 → 更新 job 的绝对路径和配置 → 重新注册并启动 → 检查健康。失败保留旧包和配置，按适配器允许的方式恢复；数据库继续遵守禁止跨大版本直接复用数据目录的限制。

长任务必须有操作 ID、阶段、结果和可恢复状态。App/CLI 异常退出后，以实例记录、launchd 状态和健康检查重新对账，不能只凭历史 PID 判断归属。有限时任务中断不代表成功，重新打开应用时提供重试或清理入口。

项目操作采用显式资源锁：下载按包锁定、实例操作按实例锁定、代理配置串行应用。取消和回滚只作用于本次操作拥有的资源。卸载包前检查实例和 job 引用；移除实例时先解除自有 job 注册，再处理记录，数据库数据按单独的删除规则保留或清理。

## 10. 首版实施里程碑

以下工期为两名开发者持续投入、具备 macOS 测试设备条件下的初步估算，不是交付承诺。M0 后依据二进制包和系统权限验证结果重新估算；单人实施需相应延长。

| 里程碑 | 预计耗时 | 交付内容 | 进入下一阶段的条件 |
| --- | --- | --- | --- |
| M0：关键验证 | 1–2 周 | Go 标准库代理、CA 信任、hosts、443；首批六软件 Apple Silicon 包来源；独立数据库目录运行 | 不要求 Homebrew，完成 HTTPS 代理和数据库初始化实验；冻结版本兼容矩阵 |
| M1：HTTPS 基础 | 2–3 周 | 站点规则、受限系统操作、证书状态、热加载、独立代理入口 | 两个已有本地服务通过可信域名访问，失败回滚可用 |
| M2：项目与运行时 | 2–3 周 | 项目导入、持久化、PHP/Node.js 下载、版本锁、项目命令环境 | 两个项目使用不同版本，GUI/CLI 看到一致配置 |
| M3：服务与数据库 | 3–4 周 | 复用 launchctl 托管实例、依赖编排、四种数据库实例、凭据、备份恢复 | 应用等待数据库就绪后启动，数据恢复和共享实例场景通过 |
| M4：整合与发布 | 2–3 周 | 完整导入流程、故障诊断、迁移回归、Developer ID 签名、开源文档；用户暂缓 Apple 公证 | 按用户指定的当前已安装 macOS 验收，发布包内声明与实际二进制一致 |

顺序执行约 10–15 周；这是功能开发与集成估算。若需要建立数据库二进制构建链，另预留 2–4 周风险缓冲。首版是否完成由验收门槛决定，不能用已有 HTTPS 演示代替整体交付。

关键依赖：M0 决定包来源和系统权限方案；M1、M2 为 M3/M4 提供基础；PostgreSQL 备份恢复和 Apple Silicon 安装是发布阻断项。

## 11. 验证计划

每个新增模块保留可替换的命令和下载接口，延续现有测试习惯；真实服务测试使用专用临时目录和独立端口，不触碰开发者原有数据库。

| 场景 | 必须通过的结果 |
| --- | --- |
| 当前已安装 macOS | 使用独立目录与端口完成闭环；App 管理二进制，安装和运行不要求 Homebrew 或本地编译工具链。其他系统/机器不属于本轮验收范围 |
| Node.js + PostgreSQL 项目 | 下载指定版本、初始化数据库、安装项目依赖、启动、可信域名访问完整通过 |
| 六类软件管理 | PHP/Node.js 项目实际执行；四引擎的认证、库/用户及备份恢复正常。Go/Valkey 仅保留旧适配兼容，不替代六类首版软件 |
| 两项目并行 | 不同运行时、端口和数据目录互不干扰；停止一个不影响另一个 |
| 仅代理已有服务 | 不安装运行时或数据库也能配置 HTTPS，移除规则不停止外部服务 |
| HTTPS 真实浏览器 | Chrome 无警告；WebSocket、HMR、SSE、上传正常 |
| 权限与网络冲突 | 拒绝授权、现有 hosts 冲突、443 被占用时可理解、可重试，不破坏原配置 |
| 版本与下载异常 | 锁定版本不可用、包摘要错误、解压失败、下载中断时没有假成功 |
| 数据安全 | 备份恢复结果一致；删除项目和卸载包不误删数据；不允许跨大版本直接打开旧数据目录 |
| 生命周期 | 关闭 GUI 后托管服务继续运行；App/CLI 中断、重启应用、重启系统后状态与实际资源一致，项目登录自启按依赖顺序执行 |
| 旧功能回归 | Homebrew、launchd、登录项及菜单栏原有操作保持可用 |
| 发布包 | 仅 Apple Silicon（arm64）验证，Intel 不在支持范围；Developer ID 签名、镜像、最低系统声明及首次启动检查通过；按用户选择暂缓 Apple 公证 |

复用 `go test ./...` 作为基础检查，并增加包安装、进程编排、代理和数据库集成测试。UI 快照不能代替真实浏览器的证书信任测试；终端启动不能代替 Finder 启动时的权限测试。

## 12. 风险与实施决策

| 风险 | 应对 | 决策时间 |
| --- | --- | --- |
| 数据库包不具备可迁移性，或缺少目标架构 | M0 实测动态库、路径、签名与初始化；必要时建立公开构建配方，不默默回退 Homebrew | M0 |
| 最低 macOS 与新工具链/软件包不兼容 | 分别验证应用和包；明确禁用不支持的组合，调整兼容目标需记录原因 | M0 |
| 本地 CA 或 hosts 状态被其他软件修改 | 独立 CA、归属标记、重新检测、冲突提示及修复，不覆盖未知内容 | M1 |
| 原有 UI 状态结构随功能增加而失控 | 提取控制层和领域状态；保持旧 Provider 通过适配层工作 | M2 前 |
| 运行时版本隔离被动态库和环境变量破坏 | 验证包完整依赖，显式构造进程环境；不依赖开发机器的全局安装 | M2/M3 |
| 数据误删或升级造成不可逆变化 | 删除分级、恢复演练、版本绑定、首版禁用跨大版本原地迁移 | M3 |
| 同时支持的软件过多导致无法维护 | 首版锁定 PHP、Node.js、MySQL、PostgreSQL、Redis、MongoDB，限制每类软件的受支持版本 | 全程 |

首版完成的判断：用户在没有 Homebrew 的 Mac 上导入一个受支持项目，按项目安装所需运行时，创建并连接数据库，启动整组服务，最后通过稳定且可信的本地域名访问；停止、重启、排错和数据恢复也有完整路径。
